01

结论摘要

这是一个完成度明显高于常见“AI 套壳项目”的作品。它没有把模型输出直接当教学结果，而是把答案、评分规则、掌握度推导全部收回服务端，并用 8 个白名单工具约束模型的输出形态。端到端链路（流式回答 → 工具出题 → 服务端判题 → 写证据 → BKT 更新 → 跨会话保留）在真实浏览器里跑通了，91 项自动化断言全绿。

但它有一个必须修的问题：“删除会话并连带删除证据”之后，知识点上的掌握度与证据计数没有重算，档案里会留下一条证据已经不存在、却仍显示“已作答 3 次、p=0.49、正在学习”的幽灵记录。对于一个把“证据可追溯”当作核心卖点的产品，这不是小瑕疵。此外，复习调度的难度/遗忘参数在调用处被写死、每轮提示词重复注入用户消息、以及证据标记依赖前端自报，都会让“可信”二字打折扣。

放行条件：修复 P1（会话删除后的聚合重算）；P2-1 ~ P2-3（复习参数、提示词重复注入、证据自报）在首次对外分发前完成。P2-4、P2-5 与全部 P3 可排入后续迭代。未发现阻塞级（P0）缺陷。

缺陷清单

按影响排序。每条都给出可定位的文件、复现证据与修复方向。

P1 · 必须修src/lib/db/repo.ts:123-134

删除会话并连带删除证据后，知识点统计不重算

deleteSession(id, { withEvidence: true }) 只删掉 attempts / exercises / evidence 三张表的行，却没有回写 concepts 上的 evidence_count、p_mastery、status、wrong_streak 等聚合字段。结果是证据已经不存在，档案仍然显示旧的掌握度。

同一路径还会留下指向已删除证据的复习条目（review_items），理由是“连续 2 次答错”，但那两次作答已经被删了。

[探针B] 删除前: evidence 行=3, concept.evidenceCount=3, p=0.489, status=learning 删除后: evidence 行=0, attempts 行=0, concept.evidenceCount=3, p=0.489, status=learning
修复方向：在同一事务里按剩余 evidence 重算该会话涉及知识点的聚合值（无证据则回到 untouched / 0.1），并清理相关 open 状态的复习条目；重算逻辑抽成一个函数，供“删会话”“删单条证据”共用。
P2 · 首次分发前修src/lib/db/repo.ts:585-594

复习调度的 difficulty / lapses 在调用处被写死

scheduleNext() 本身实现没问题，但调用时传的是 difficulty: 5、lapses: 0、reps: concept.evidenceCount。于是每次调用都从“难度 5、遗忘 0 次”重新开始：难度永远在 5 附近抖动，遗忘次数记一次就被下一次清零。

[探针A] 第1次(错) difficulty=5.20 lapses=1 reps=0 第2次(对) difficulty=4.95 lapses=0 reps=2 第3次(对) difficulty=4.95 lapses=0 reps=3 第4次(对) difficulty=4.95 lapses=0 reps=4

实际效果是调度退化成“只看 stability 的间隔增长”，README 里“FSRS 启发式、难度与遗忘参与调度”的描述只兑现了一半。

修复方向：传 concept.difficulty / concept.lapses / concept.reps；补一条“连续答错应让间隔收敛”的回归测试。
P2 · 首次分发前修src/app/api/chat/route.ts:43-49 + src/lib/ai/prompt.ts:142-174

每轮提示词重复注入当前用户消息，并夹带空助手占位

用户消息在构建提示词之前就已写入数据库，buildHistory() 会把它读进历史；随后 buildTeachingMessages() 又在末尾追加了一次同样的文本。中间那条刚创建的 status: "streaming" 空助手消息则被渲染成 （空）。

[探针C] 末尾消息序列: system: "# 当前学习者上下文…" user: "请解释机会成本" assistant: "（空）" user: "请解释机会成本" 同一用户消息出现次数: 2

每轮多付一次输入 token 是小事；更要紧的是模型看到“用户连说两遍、中间夹一条空回复”，容易重复回答或误判轮次。

修复方向：构建消息时排除本次刚落库的 user 消息（或先构建再落库）；buildHistory() 跳过 content 为空且 status=streaming 的助手消息。
P2 · 首次分发前修src/app/api/exercises/[id]/solution/route.ts + src/app/api/attempts/route.ts:12-19

“是否看过解析 / 是否用了提示”完全依赖前端自报

/solution 明确不写任何服务端状态，提交时 viewedSolution 与 usedHint 由请求体决定。也就是说，先调一次 /solution 拿到答案，再以 viewedSolution: false 提交，这次作答会被当成“独立完成”计入掌握度。

对单机自用工具，这可以解释为“防君子不防小人”；但这个产品的核心卖点就是“可追溯、可信的学习证据”，证据链第一环由被考核者自己填写，逻辑上是闭环不了的。

修复方向：/solution 在服务端给 exercise 或 block 打一个 solution_viewed_at 标记，提交时以服务端标记为准；提示同理，用服务端发放记录覆盖客户端布尔值。
P2 · 排期修src/components/blocks/ExerciseBlock.tsx:158-176

幂等键每次点击都新生成，服务端去重覆盖不到真正的重复提交

idempotencyKey: uuid() 在 submit() 内部生成，两次调用必然得到两个不同的键。目前只靠 pending 状态挡重复点击，而 setPending(true) 是异步渲染，快速连点存在竞态窗口；网络层的自动重试同样会拿到新键。

README 写的“重复点击 / 重复提交只计一次证据”，严格说只对“同一个键的重复请求”成立，而客户端并不会复用这个键。

修复方向：幂等键按“练习 + 草稿内容”生成并缓存在 ref 里，提交成功后再清空；或服务端增加“同一练习 N 秒内的相同作答”去重。
P2 · 分发前处理src/middleware.ts / src/app/api/system/route.ts / src/app/api/ai/test/route.ts

默认监听全网且无鉴权，配套接口存在信息暴露与内网探测面

不带 APP_ACCESS_TOKEN 时中间件直接放行，而 next start 默认绑定 0.0.0.0。启动日志实测显示 Network: http://10.12.126.88:3211，同一局域网内任何人可读写学习档案、改模型配置。

在此基础上：/api/system 返回数据库绝对路径、Node 版本与平台；/api/ai/test 会把模型返回内容回显，而 baseUrl 可由设置接口改成任意地址——等于给内网探测提供了一个低带宽的读取通道（代码审查结论，未做攻击验证）。

修复方向：默认绑定 127.0.0.1，或首次启动自动生成随机 token 并在控制台打印访问链接；/api/system 去掉路径等敏感字段；ai/test 的 detail 截断并脱敏；补 CSP / X-Frame-Options / Referrer-Policy。
P3 · 体验src/components/blocks/SimulatorBlock.tsx:219-246

模拟器曲线图的 Y 轴刻度会被裁切、并与轴标题重叠

刻度文字以 x = pad.l - 6 = 36 右对齐，而左边距只有 42；八位数（如 19744.58）向左展开约 42px，直接越出 SVG 视口。截图里 19744.58 左侧被切、6522.29 与竖排轴标题叠在一起。

修复方向：按最长刻度动态计算左边距，或刻度改用紧凑记法（1.97 万）；轴标题与刻度分列两个槽位。
P3 · 资源src/app/api/materials/route.ts:26-31

解析失败或不支持的文件仍然落盘，且没有清理入口

无论 parseMaterial() 返回 failed 还是 unsupported，路由都会把原始文件写进 data/uploads。超过 20MB 被拒的文件也一样。界面上没有“材料管理/删除”入口（DELETE 接口存在但未接入 UI），文件只进不出。

修复方向：状态非 parsed 时不落盘；或提供材料列表与删除按钮，并在设置页展示占用空间。
P3 · 数据语义src/lib/db/repo.ts:445-463

“零证据空壳”清理会误伤“看过解析未计分”的知识点

判定条件是 evidence_count = 0。用户如果练习过、但每次都看了解析（按设计不计入掌握度），该知识点的 evidence_count 仍为 0，会被一键清理掉；清理时 attempts.concept_id 被置空，作答记录还在，但已经指不回任何知识点，审计链断掉。

修复方向：把“有 attempts 但无 evidence”排除在空壳之外，或在清理确认框里单独统计并提示这一类。
P3 · 性能src/lib/db/repo.ts:923-951

材料检索每轮把全部切片读进内存做子串匹配

单文档最多 400 个切片，searchMaterialChunks() 每次对话都 select 全表再在 JS 里 includes。材料达到几十份时，每条消息都要搬运数万行文本。README 已声明“关键词检索而非向量检索”，但没有提到这个全表扫描的实现代价。

修复方向：用 SQLite FTS5 建虚拟表，或至少先在 SQL 里用 LIKE 过滤再加权重排序。
P3 · 文档README.md:74 / 构建输出

文档表述与构建警告的小幅漂移

README 称数据模型为“21 张表”，实测数据库为 23 张（即使剔除 schema_migrations 与 users 才是 21，读者按字面理解会对不上）。构建有 2 条警告：middleware 约定在 Next 16 已弃用（应迁移到 proxy）；Turbopack 因 dataDir() 里的动态路径把整个项目纳入 NFT 追踪。

修复方向：修正表数量表述（或注明统计口径）；把 src/middleware.ts 迁移为 proxy.ts；给 path.join(process.cwd(), 'data') 加 turbopack 静态作用域或忽略注释。
P3 · 工程配套package.json / 仓库根目录

缺少版本控制与持续集成，依赖未声明运行时约束

仓库没有 .git，也没有 CI 配置；package.json 未声明 engines，而启动脚本实际上要求 Node 20+；pdf-parse 仍停留在 1.1.1（多年未更新，且以“加载测试文件失败”闻名）。这些不影响当前运行，但会让复现、回滚和协作变困难。

修复方向：初始化 git 并保留当前基线提交；加一条最简 CI（install + build + test）；声明 engines.node >= 20；评估 PDF 解析替换方案（如 pdfjs-dist）。

06

做得好的地方

产品判断力

  • 没有模型就明说。未配置时直接告知“无法真正教学”，不拿固定话术假装上课——这是很多同类产品做不到的克制。
  • 答案隔离是真做了。答案与评分规则只存 exercises.answer，下发的 ExercisePublic 不含答案；端到端断言里专门有一条“响应中不含 answer 字段”。
  • 开放题不伪造判分。模型不可用时标记“未评阅”，明确不计入掌握度，而不是随机给个分。
  • 掌握度只能由证据推导。状态机阈值全部写死并给出原因文本，单次答对不足以“掌握”，同题刷多遍不会堆出掌握度。

工程与文档

  • 代码卫生罕见地好。全量扫描：0 个 any、0 个 console.log、0 个 TODO/FIXME、无硬编码密钥；模拟器表达式用自研词法/语法分析，明确不用 eval。
  • 边界处理完整。流式中断保留已生成内容；工具参数 zod 校验失败降级为文字；组件有 ErrorBoundary；非法 LaTeX 与异常计划块都有回归测试。
  • 数据模型克制。23 张表把“会话 / 证据 / UI 状态”分开，删除会话默认保留证据，审计表齐全。
  • 开源合规认真。THIRD_PARTY_NOTICES.md 连“为什么没用某个库”都写了，并附 MIT 原文；docs/OPEN_SOURCE_RESEARCH.md 记录了检索方式、star 数、源码级结论与取舍。
